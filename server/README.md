# HoldMate backend

Node.js + Express + MongoDB (Atlas, via Mongoose) + Socket.IO.
It serves the API **and** the website, so everything runs at **http://localhost:5000**.

---

## 1. Install

Requires Node.js 18 or newer.

```bash
cd server
npm install
```

## 2. Create `server/.env`

Copy `.env.example` to `.env` and fill it in:

```env
PORT=5000
MONGODB_URI=mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/holdmate?retryWrites=true&w=majority
JWT_SECRET=<long random string, 32+ characters>
NODE_ENV=development
HUB_LAT=10.9965
HUB_LNG=76.9667
SERVICE_RADIUS_KM=15
SMS_PROVIDER=console            # or messagecentral / msg91 / fast2sms (see section 5)
MC_AUTH_TOKEN=                  # Message Central dashboard token (preferred)
MC_CUSTOMER_ID=                 # fallback, only if MC_AUTH_TOKEN is empty
MC_KEY=
```

- Generate a JWT secret: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`
- In MongoDB Atlas, open **Network Access** and allow your IP address.
- URL-encode special characters in the database password (`@` → `%40`, `#` → `%23`, …).
- Optional: `CORS_ORIGINS=http://127.0.0.1:5500,http://localhost:5500` if you open the frontend on another origin
  (for example VS Code Live Server). Recommended: just use http://localhost:5000.

`.env` is in `.gitignore` — never commit it.

## 3. Seed the database

```bash
npm run seed
```

**This clears all HoldMate collections** and then creates the test accounts, the fleet with lockers and the demo booking.

## 4. Run

```bash
npm run dev     # with auto-restart (nodemon)
npm start       # production style
```

Open **http://localhost:5000**.

## 5. Login codes by SMS (switching providers)

Login OTPs go through one interface, `src/services/sms/index.js` (`sendOtp(phone)` / `verifyOtp(phone, code)`).
Pick the provider with `SMS_PROVIDER` in `server/.env` and restart the server:

| `SMS_PROVIDER` | What happens | Required `.env` keys |
| --- | --- | --- |
| `console` (or empty) | Code is printed in the server terminal. **Development only**: the server refuses to start with it when `NODE_ENV=production`. | none |
| `messagecentral` | Message Central VerifyNow sends the SMS and checks the code (we store only its `verificationId`). | `MC_AUTH_TOKEN` (preferred), **or** `MC_CUSTOMER_ID` + `MC_KEY` (Base64 of your Message Central password) |
| `msg91` | MSG91 OTP API sends and checks the code. | `MSG91_AUTH_KEY`, `MSG91_TEMPLATE_ID` |
| `fast2sms` | Fast2SMS delivers a code generated by the server (stored as a bcrypt hash). | `FAST2SMS_API_KEY` |

The server checks these keys at start-up and stops with a clear message if one is missing.

**Message Central authentication:**
- **`MC_AUTH_TOKEN` (recommended):** copy the ready Auth Token from
  console.messagecentral.com → Developer Guide → API Credentials. It is sent as-is in the `authToken` header for
  sending and checking codes; the token API is not called.
- **Fallback, only when `MC_AUTH_TOKEN` is empty:** `MC_CUSTOMER_ID` + `MC_KEY`. The server requests a token from
  the token API, keeps it in memory and fetches a new one if a call returns 401.
- If Message Central answers 401 while using `MC_AUTH_TOKEN`, the server logs:
  *"Message Central auth token expired or invalid — copy a new one from console.messagecentral.com → Developer Guide → API Credentials"*.
  Paste the new token into `server/.env` and restart. Customers see "We couldn't send the code. Please try again in a minute."

> **MSG91 needs DLT registration first.** Indian telecom rules (TRAI DLT) require a registered entity (PE ID),
> sender ID (header) and an approved OTP template before MSG91 can deliver SMS in production. Complete DLT
> registration and get the template approved, then put its ID in `MSG91_TEMPLATE_ID`.

**Check the credentials without sending an SMS:**

```bash
npm run sms:check
```

For Message Central it uses `MC_AUTH_TOKEN` (or gets a token from `MC_CUSTOMER_ID` + `MC_KEY`) and makes a harmless
`validateOtp` call with a dummy ID. A working token gets *"verificationId is invalid or expired"* (expected);
an invalid one gets the 401 message above. It never prints the token or keys, and no SMS is sent.

**Rules (all providers):** Indian mobiles only (10 digits starting 6–9; `+91`, `91` or `0` prefixes are accepted
and removed) · code valid 5 minutes · 5 wrong attempts, then a new code is needed · 1 code per number per
60 seconds · max 5 codes per number per hour and 10 per IP per hour (only codes actually sent count) · the OTP
is never returned by the API · if the provider fails the user sees "We couldn't send the code. Please try again
in a minute." and the provider's error is logged on the server (without keys, tokens, URLs or codes).

**Test a real SMS on your own phone (Message Central):**
1. Set `SMS_PROVIDER=messagecentral` and `MC_AUTH_TOKEN` in `server/.env`, then run `npm run sms:check`: it must say *credentials work*.
2. `npm run dev`, open http://localhost:5000 and click the person icon (**My bookings**).
3. Enter your own mobile number and tap **Send code**. The SMS should arrive within a few seconds.
4. Type or paste the 6 digits (on phones, the keyboard offers to fill the code). It logs in automatically.
5. If it fails, read the `[sms] messagecentral …` line in the server terminal for the provider's error.

**Adding another provider:** create `src/services/sms/providers/<name>.js` with `send(phone)` (return `{ code }`
if you generate the code, or `{ ref }` if the provider checks it) and `verify(phone, code, ref)` when the provider
checks codes; register it in `src/services/sms/index.js` and add its keys to `config/env.js` and `.env.example`.

### Try the full flow
1. On the website: **Book now** → route → bags & details → verify your phone with the 6-digit code (SMS, or the server console with `SMS_PROVIDER=console`) → confirmed (note the booking ID and 4-digit handover OTP).
2. **My bookings** (person icon in the navbar) → **Track**.

## API

All responses are JSON. Errors look like `{ "error": { "message": "...", "code": "...", "details": [...] } }`.
Every route validates its input with zod; unknown fields are rejected.
Auth is a JWT in the httpOnly cookie `hm_token` (7 days). `Authorization: Bearer <token>` also works for apps/tools.

### Auth (rate-limited)
| Method | Path | Body | Notes |
| --- | --- | --- | --- |
| POST | `/api/auth/request-otp` | `{ phone }` | sends a 6-digit code via `SMS_PROVIDER`; valid 5 min; 1 per number / 60 s, 5 per number / hour, 10 per IP / hour; returns `{ channel, expiresInSeconds, resendAfterSeconds }`, never the code |
| POST | `/api/auth/verify-otp` | `{ phone, otp, name? }` | max 5 wrong attempts per code; creates the customer on first login; sets the cookie |
| GET | `/api/auth/me` | — | `{ user }` (or `{ user: null }` when logged out) |
| POST | `/api/auth/logout` | — | clears the cookie |

### Places & pricing (public)
| Method | Path | Notes |
| --- | --- | --- |
| GET | `/api/places` | hub, radius and Coimbatore landmarks |
| POST | `/api/quote` | `{ serviceType, pickup?, drop?, distanceKm?, hours, bags, weightKg }` → price breakdown, suggested vehicle, zone check |

Pricing (all in `src/config/pricing.js`): base ₹49 + ₹9/km + ₹6/hour (₹3/hour after 24 h) + ₹3/kg over 5 kg;
Scheduled ×0.85, Express ×1.5; Store-only has no distance charge; Events = ₹1499 + ₹20/bag.
Distance = haversine × 1.3. Vehicle: Bike ≤2 bags & ≤15 kg, Auto ≤8 bags & ≤80 kg, Van ≤250 kg, Truck for events or >20 bags.

### Bookings (customer, logged in)
| Method | Path | Notes |
| --- | --- | --- |
| POST | `/api/bookings` | validates zone/time, recalculates the price, assigns vehicle + locker, returns the handover OTP **once** |
| GET | `/api/bookings` | my bookings |
| GET | `/api/bookings/:id` | my booking |
| PATCH | `/api/bookings/:id/cancel` | free until 1 hour before pickup; frees the locker |

### Tracking & vehicles
| Method | Path | Who | Notes |
| --- | --- | --- | --- |
| GET | `/api/track/:bookingId` | public | status, timeline, vehicle, locker, places, latest location, ETA (no phones/OTPs) |
| GET | `/api/vehicles` | public | fleet summary with locker counts |
| GET | `/api/vehicles/:id/lockers` | public | `:id` = code (HM-01) or Mongo id |
| POST | `/api/vehicles/:id/location` | captain of that vehicle / admin | `{ lat, lng, speed?, heading? }` → saved + broadcast |

### Captain (role `captain`; admins can also use these)
| Method | Path | Notes |
| --- | --- | --- |
| GET | `/api/captain/jobs` | active jobs + today's pickups (IST) on my vehicles, with customer name/phone |
| PATCH | `/api/captain/bookings/:id/status` | `{ status }` in order: `picked_up → in_locker → on_the_way → arrived` (optional `photos` on pickup) |
| POST | `/api/captain/bookings/:id/handover` | `{ otp }` → `delivered`, frees the locker (locks after 5 wrong OTPs) |

### Admin (role `admin`)
| Method | Path | Notes |
| --- | --- | --- |
| GET | `/api/admin/bookings` | `?status=&date=YYYY-MM-DD&page=&limit=` |
| GET | `/api/admin/stats` | bookings by status, today, booked value, lockers, vehicles, customers |
| PATCH | `/api/admin/bookings/:id/assign` | `{ vehicleId }` (code or id) — moves the booking to a free locker on that vehicle |
| GET/POST | `/api/admin/vehicles` | list / create (lockers created automatically) |
| PATCH/DELETE | `/api/admin/vehicles/:id` | update (type, status, captainId, lockerCount when all free) / delete (no active bookings) |
| GET/POST | `/api/admin/captains` | list / create (promotes an existing customer with that phone) |
| PATCH/DELETE | `/api/admin/captains/:id` | update / delete (unassigns their vehicles) |

### Socket.IO
The browser loads `/socket.io/socket.io.js` from this server, then:
- emits `track:join` with a booking ID (acknowledged with `{ ok }`)
- receives `vehicle:location` `{ bookingId, vehicle, lat, lng, speed, heading, at, eta }`
- receives `booking:status` `{ bookingId, status, statusHistory, eta }` and `booking:assigned`

## Project layout

```
server/
  src/
    index.js              Express app, security middleware, static frontend, Socket.IO, start-up
    seed.js               test data
    config/               env.js (loads .env), db.js, pricing.js (ALL rates), places.js
    models/               User, Otp, Vehicle, Locker, Booking, LocationPing
    routes/index.js       every route + its zod schema + role guard
    controllers/          auth, public (places/quote/track), bookings, vehicles, captain, admin
    middleware/           auth (JWT cookie + roles), validate (zod), rateLimit, error
    services/             pricing, booking (lockers/ETA/views), realtime (Socket.IO),
                          sms/ (index.js interface, providers/console|messagecentral|msg91|fast2sms, check.js)
    utils/                geo, ids, schemas, time, AppError, asyncHandler
  requests.http           all endpoints for the VS Code REST Client extension
```

Security: helmet (with a Content-Security-Policy that only allows the CDNs/APIs the site uses), CORS allow-list,
rate limiting on OTP and handover routes, zod validation everywhere, OTPs hashed (bcrypt) or checked by the SMS provider, JWT in an httpOnly
`SameSite=Lax` cookie (`Secure` in production), central JSON error handler, only `index.html`, `css/`, `js/` and
`assets/` are served — never `server/` or `.env`.

Data retention: OTP documents expire automatically after 5 minutes; GPS pings (`LocationPing`) after 7 days.
